# Design: chart 0.1.0 — org-pack-first vision, private data packs, evidence publishing, recipe visibility

Chart: `nvidia-aicr`
Target version: 0.1.0 (the initial release; earlier internal iterations
were never published)
Date: 2026-08-07 (merged same-day with the vision deep-dive)
Status: implemented (working tree, unreleased); amendments in-line where
implementation corrected the design

This document merges two brainstorms that turned out to be one subject: the
feature spec for private `--data` packs and evidence publishing, and the
end-user deep-dive that asked whether the Job does what a user envisions at
all. The deep-dive's answer reframes the features: **the org data pack is the
product; everything else supports it.**

## 1. The user model — who is this chart actually for?

### 1.1 What the deep-dive established (all verified against aicr v0.18.0)

**Recipe selection is criteria assembly; there is no name selector.**
`aicr recipe` has no `--recipe-name`/`--from` flag. The only way to select a
recipe is to state criteria dimensions (`service`, `accelerator`, `intent`,
`os`, `platform`) and let the resolver match overlays. The embedded catalog
has ~101 entries of which **45 are leaves** (deployable recipes); the rest are
intermediate nodes.

**Under-specification degrades silently.** Every row below exits 0:

| Criteria stated | Resolution |
|---|---|
| `any` + `a100` | **11 components**, 3 overlays |
| `kind` + `h100` + `training` | 12 components, 5 overlays |
| `eks` + `h100` + `training` | 14 components, 6 overlays |
| `eks` + `gb200` + `training` + `ubuntu` + `kubeflow` | **15 components**, 8 overlays |

A user who under-specifies gets a thinner stack — no `aws-efa`, no CSI driver,
fewer overlays — with no warning of any kind. This is worse than the hard
failure because it looks like success.

**Over-specification fails hard, with a good message.**
`--accelerator h100 --intent training` (service `any`):
`[INVALID_REQUEST] intent 'training' requires additional criteria; supported
combinations: (service=aks), (service=bcm), (service=eks), (service=kind)...`
Exit 2, Job dies. Correct — but the user learns it ~2 minutes into a Job run
(after a ~1 GB image pull and binary download), from pod logs, long after
`helm install` reported success.

**Accelerator-less leaves exist.** `service: bcm, intent: inference` resolves
to a full 14-component leaf with no accelerator stated. Explicit
`--accelerator any` is rejected ("no criteria provided") — "any" is the
absence of a value, not a value.

**The pre-release defaults sat on the worst square.**
`accelerator: a100, service: any` is the thinnest resolution in the table
above, shipped as the out-of-the-box default.

### 1.2 The org-pack pattern: `--data` packs are named recipes

All public docs (this spec, the chart README) use a **synthetic** organisation
("acme") to illustrate the pattern. Internal pack examples must not appear in
this repository; the pattern itself is built entirely from upstream's public
`docs/integrator/data-extension.md` mechanics and has been validated
end-to-end on real H200 bare-metal hardware.

A platform team publishes one pack:

```
acme-aicr-pack/
├── registry.yaml                     # required stub even with no component
│                                     # additions (components: [])
├── overlays/
│   └── acme-h200-training.yaml       # registers service=acme; bakes in the
│                                     # org's environment profile + constraints
└── validators/catalog.yaml           # org validators, pinned by image digest
```

The overlay registers **`--data`-private criteria values** (e.g.
`service: acme`) — upstream's rule is that *"adding a new value to an overlay
automatically makes it a valid CLI input."* The same overlay carries the org's
environment facts (containerd socket, preinstalled-driver posture, fleet
constraints), so a recipe resolved via `--service acme` produces a bundle that
needs **zero manual `--set` flags** — the environment travels with the pack,
not with per-cluster values.

So: **an org pack that registers a distinctive `service` value IS the recipe
naming mechanism** AICR otherwise lacks. `--data` is exactly "a way to deploy
pre-existing recipes."

### 1.2.1 The criteria surface is closed — and the chart already exposes all of it

What can a pack user actually pass? Packs register new **values** for existing
dimensions; they cannot invent new criteria **flags**. The complete criteria
surface at aicr v0.18.0 is: `--service`, `--accelerator`, `--intent`, `--os`,
`--platform`, `--nodes`, plus `--config`/`--snapshot` inputs and the
`--criteria-strict` modifier.

The chart's coverage today:

| aicr flag | Chart value | Notes |
|---|---|---|
| `--service` | `service` | pack-private values (e.g. `acme`) pass through verbatim — the chart never validates criteria values, by design |
| `--accelerator` | `accelerator` | " |
| `--intent` | `intent` | " |
| `--os` | `os` | " |
| `--platform` | `platform` | " |
| `--nodes` | — | freeform via `recipeFlags: "--nodes 8"` |
| `--criteria-strict` | — | freeform via `recipeFlags` (already the documented example) |
| `--config` / `--snapshot` | — | not exposed; out of scope |

Empty value = flag omitted (the resolver uses its detected/any value) — that
contract is retained from the earliest drafts and is what lets pack-private values coexist
with embedded ones. So the pack user story needs **no new values plumbing**:
`service: acme, accelerator: h200, intent: training` works today, and anything
exotic rides `recipeFlags`. The guard in §6.1 never blocks pack users, because
using a pack requires `dataPack` to be set — which is the guard's first
escape clause.

### 1.3 The two users, ranked

1. **Fleet operator with an org pack (primary).** Their platform team publishes
   one pack. Every cluster states `service: <org>` plus the pack-defined
   dimensions. Resolution is deterministic, the environment travels with the
   pack, validators are org-calibrated. The Job is precisely what this user
   envisions: "converge this cluster on our named, validated recipe."
2. **Explorer on the upstream matrix (secondary).** Assembles up to five
   dimensions against the embedded catalog. Served with honest documentation
   and visibility (§5), not with guardrails that reimplement the resolver.

Consequences for the pre-release surface:

- `dataPack` is promoted from optional extra to the headline feature — which
  makes private-registry auth (§3) load-bearing, not nice-to-have.
- `environment.k0sContainerd` / `environment.preinstalledDriver` are demoted:
  kept for compatibility, documented as "environment facts that belong in your
  org pack's overlay" (§6.3).
- The `a100` default is removed (§6.1).

## 2. Scope

**In scope**

- Authenticated `dataPack` pulls from private OCI registries.
- Evidence publishing to an OCI registry from the install Job, two trust modes.
- Resolved-recipe visibility via ConfigMap capture (report-only; no preflight).
- Criteria guard: no default accelerator; render-time requirement with a
  precise escape for pack users and service+intent leaves.
- README restructure: org-pack-first narrative.
- Render-time guards and mutation-tested render assertions for all of the above.

**Out of scope**

- Preflight resolution in a separate init step, and declared-expectation checks
  (`expectComponents` etc.) — considered and rejected by decision; the recipe
  ConfigMap gives visibility without a second resolution path.
- `imagePullSecrets` for `runtimeImage`/`orasImage` — real, separate change.
- Air-gapped support — unchanged limitation; separate design.
- Private Sigstore endpoints — no aicr flags for it at v0.18.0.
- Catalog-side changes — follow-up PR after the release.
- The `--nodes` criteria flag — unexposed today, unexposed after this change.

**Compatibility.** One deliberate change versus early internal drafts: a values file that relied on the
implicit `accelerator: a100` default now fails at render with an actionable
message (§6.1). As 0.1.0 is the first published release, nothing external
breaks.

## 3. Feature A — private data packs

### 3.1 Values

```yaml
dataPack: ""            # unchanged: OCI reference, no scheme
# Name of an EXISTING Secret of type kubernetes.io/dockerconfigjson holding
# credentials for the dataPack registry. Empty = anonymous pull (public
# artifacts only). The chart never creates this Secret.
dataPackSecret: ""
```

### 3.2 Template changes (`templates/job.yaml`)

When `dataPackSecret` is non-empty, the oras initContainer gains:

- a volume mounting the Secret's `.dockerconfigjson` key to
  `/pack-auth/config.json`, `readOnly: true`, `defaultMode: 0440` (not 0400:
  secret files are root-owned and the container reads them as uid 65532 via
  fsGroup — owner-only permissions would be unreadable);
- `--registry-config /pack-auth/config.json` appended to `oras pull`.

The existing `HOME=/data/pack` env stays (oras needs writable HOME under the
read-only rootfs). When empty, the initContainer renders exactly as today.

### 3.3 Rationale and rejected alternatives

Reference-an-existing-Secret is the standard Kubernetes credential pattern and
keeps secrets out of values files, Helm release history, and — for k0rdent
users — out of `MultiClusterService` manifests in git.

Rejected: `dataPackUsername`/`dataPackPassword` values (credentials land in the
release Secret and `helm get values`); reusing pod `imagePullSecrets` (kubelet
consumes those for image pulls; in-container oras never sees them).

### 3.4 Failure mode

Bad or missing credential fails the initContainer; the main container never
starts; the Job fails visibly with the oras error in the pod log. Fail-closed,
no anonymous fallback.

### 3.5 Private validator images (added post-e2e)

A pack's validator catalog may reference private images. Those are pulled by
the kubelet in the namespace where aicr runs its validator Jobs (default
`aicr-validation`), so `dataPackSecret` cannot cover them. aicr exposes the
knobs natively (`--image-pull-secret`, repeatable; `--namespace`;
`--service-account-name` — read from the v0.18.0 binary), so the chart adds
only passthroughs, not secret machinery:

- `validateFlags` — the previously missing freeform passthrough for the
  validate stage, same word-split contract as recipe/bundle/deployFlags.
  Also carries the burn-in `--node-selector` pattern.
- `job.extraEnv` — verbatim env for the installer container, for env-shaped
  aicr knobs (e.g. `AICR_NCCL_FABRIC=roce` for benchmark catalogs).

Documented one-Secret pattern: `--namespace <release ns>` lets the same
dockerconfigjson Secret serve the pack pull, the evidence push, and the
validator pull. Not built: chart-managed secret replication into
`aicr-validation`, or first-class `validate.imagePullSecrets` values — the
freeform flag is upstream's own interface.

### 3.6 Assert-only runs (`deploy.enabled: false`, added after the validate-semantics examination)

Initially deferred, then promoted into the release once the semantics were
pinned: `aicr validate` validates the CLUSTER against the RECIPE (the
binary's own description) and never deploys; deploy-then-validate is a
workflow order the caller chooses, not aicr behaviour. The chart hard-coupled
enforcement (deploy) with verification (validate); `deploy.enabled: false`
decouples them — pack pull, recipe resolution and capture, then straight to
validation. Guard: rejected at render unless `validate.enabled`, because a
Job that neither deploys nor validates is a no-op. Proven live on the kind
e2e cluster: the assert-only revision left every component release's Helm
revision untouched while validators ran and published a second,
distinctly-fingerprinted evidence artifact.

**The two-validations model** (refined with upstream's validation.md): the
same machinery serves two verifications. Rollout verification — deployment
phase, aicr-shipped validators — asks "is the cluster running what the
recipe says?". Capability qualification — performance/conformance phases,
validators mostly from the org pack — asks "does the hardware deliver?" and
CONSUMES what rollout installed (DCGM, device plugin, drivers). Upstream
guarantees, quoted: validation "does not deploy" (components "must
pre-exist"); missing recipe components FAIL the deployment phase (exit 8);
optional prerequisites hit "explicit skip guards" that "fire before any
cluster mutation" (CTRF skipped, exit 0, not a failure); readiness
pre-flight "always fails closed" with exit 2 "even under
--fail-on-error=false"; and "an inconclusive check fails closed rather than
passing silently". The chart logs these exit-code meanings inline. The four
resulting postures (install-and-prove / qualify-hardware / drift-check /
full-acceptance) ship as worked values files in `examples/`.

**Values-shape decision**: the toggle is `deploy.enabled` (a `deploy:` leg
block) rather than a loose top-level bool or a `mode:` enum — legs get
blocks (symmetric with `validate:`, extensible to future upstream verbs like
snapshot/diff, with room for a future `deploy.deployer`); postures are
combinations and live in docs/examples, not in the API; the per-verb
`*Flags` passthroughs stay top-level as a family.

## 4. Feature B — evidence publishing

### 4.1 Upstream facts (verified against the v0.18.0 binary)

`aicr validate --emit-attestation <dir>` writes a `summary-bundle/` (recipe,
snapshot, CycloneDX BOM, CTRF, manifest, unsigned in-toto statement).
`aicr evidence publish [options] <bundle-dir>` signs and pushes an
already-emitted bundle and writes `pointer.yaml` — upstream built it exactly
for our split:

> This decouples the cluster-bound validate step from the Fulcio/Rekor-bound
> signing step so they can run on different networks.

and guarantees the artifact is content-addressable and identical regardless of
which host runs which leg. Flags: `--push <ref>` (required),
`--identity-token` (env `COSIGN_IDENTITY_TOKEN`), `--no-sign`,
`--insecure-tls`, `--plain-http`, `--yes`. The sign-later leg is
`aicr evidence sign <pointer> [--relocate]`.

Keyless identity precedence: `--identity-token` > `COSIGN_IDENTITY_TOKEN` >
ambient GitHub Actions OIDC > device flow > browser. Public Fulcio trusts
managed-cloud cluster issuers and GitHub Actions — **not** self-managed k0s
issuers, which is why the token is BYO (decision §10).

Signing attaches via the OCI 1.1 Referrers API (GHCR, GitLab, Harbor ≥2.8,
ECR, Artifact Registry, ACR, Artifactory) with a tag-schema fallback.

### 4.2 Values

```yaml
validate:
  enabled: false
  emitEvidence: false
  evidenceConfigMap: aicr-evidence-bundle
  publish:
    enabled: false          # requires emitEvidence
    mode: signed            # signed | unsigned
    ref: ""                 # OCI push ref, e.g. ghcr.io/myorg/aicr-evidence. Required.
    identityTokenSecret:    # mode=signed only: short-lived OIDC token
      name: ""
      key: token
    registrySecret: ""      # dockerconfigjson for the push; empty = anonymous
    failOnError: false      # publish failure fails the Job only when true
    insecureTLS: false
    plainHTTP: false        # local registry testing
```

### 4.3 Script flow

Publish slots between CTRF capture and evidence capture — ordering matters
because `evidence publish` writes `pointer.yaml` **into** the bundle directory,
so capturing afterwards archives the bundle with its own locator:

1. `aicr validate …` — unchanged; `rc` captured.
2. CTRF → `resultConfigMap` — unchanged, unconditional.
3. **New:** if `publish.enabled` and `./evidence` exists:
   `aicr evidence publish ./evidence --push "$PUBLISH_REF" --yes`
   (+ `--no-sign` for unsigned mode, `--insecure-tls`/`--plain-http` as set),
   exit code in separate `prc`. `--yes` is explicit — a Job must not depend on
   TTY detection.
4. Evidence tarball (+ new plaintext `pointer.yaml` key) → `evidenceConfigMap`.
5. Validation `failOnError` gate on `rc` — unchanged.
6. **New:** publish `failOnError` gate on `prc`.

### 4.4 Environment

`mode=signed` adds `COSIGN_IDENTITY_TOKEN` via `secretKeyRef`. The variable is
**absent entirely** in unsigned mode — not empty — so an unsigned run can never
pick up a stale identity. `publish.registrySecret` mounts at
`/publish-auth/config.json`; `DOCKER_CONFIG=/publish-auth` is set **only on
the publish invocation itself**, not container-wide, so the push credential
can never leak into `deploy.sh`'s helm pulls.

### 4.5 Trust model, stated plainly

**`mode: signed`** puts a Sigstore identity token inside a pod whose SA is
bound to cluster-admin. Anyone who can read pods or exec in that namespace
during the run can sign as that identity until the token expires. Acceptable
only for short-lived, per-run tokens.

**`mode: unsigned`** never admits identity to the cluster: push unsigned with
an empty signer block, sign later from a trusted host with
`aicr evidence sign <pointer> --relocate` (upstream's fork-based CI flow).
Recommended posture for regulated environments and for scheduled runs.

Token freshness is the operator's contract: the Secret must hold a token valid
at Job runtime. The README documents the CI pattern (mint → write Secret →
install) and warns that a token minted at `helm install` time may be expired
by the time a long `deploy.sh` run reaches validation — a real hazard that
also argues for `unsigned`.

## 5. Feature C — resolved-recipe visibility (report-only)

The chart's answer to silent under-specification (§1.1) is visibility, not a
second resolver. Immediately after `aicr recipe` succeeds:

- **`summary.txt`** → `recipeConfigMap` (default `aicr-recipe`, capture on by
  default; `recipeConfigMap: ""` disables): criteria as actually passed,
  component count, sorted component names, overlay count. One
  `kubectl get cm aicr-recipe -o jsonpath=...` answers "did I get the stack I
  meant?" — an 11-vs-15 discrepancy is visible in one line.
- **`recipe.yaml`** → same ConfigMap, second key, behind the same ~900 KiB
  budget guard as the evidence capture (the kind-run recipe was ~81 KiB).

Implementation reuses the existing `kubectl create configmap --dry-run |
kubectl apply --server-side` pattern from the CTRF capture. aicr natively
supports `-o cm://ns/name`, but the Job needs `recipe.yaml` as a local file
for `aicr bundle`, so file-then-capture is the simpler single path.

Considered and rejected by decision: a preflight init step resolving the
recipe before the heavy install, and operator-declared expectations
(`expectComponents:`). Report-only keeps one Job and no duplicated resolution;
the cost — a misresolved recipe still burns a full install before anyone
looks — is accepted.

## 6. Feature D — defaults, guard, and docs restructure

### 6.1 No default accelerator

`values.yaml` ships `accelerator: ""`. Render fails when **all** of the
following hold: `accelerator` empty, `dataPack` empty, and NOT (**concrete**
`service` and `intent` both non-empty). "Concrete" excludes `any` — the
chart's `service` default — because aicr rejects `any`+intent outright;
without this exclusion, setting only `intent` would slip the guard and then
hard-fail inside the Job, which is precisely what the guard exists to prevent.
(Implementation note discovered during build; the guard as first drafted said
only "non-empty".)

Two refinements from code review: "concrete" also excludes aicr's documented
aliases of `any` (`self-managed`, `self`, `vanilla` — values.yaml documents
them, so the guard must too), and `accelerator: "any"` fails render with its
own message rather than merely not counting as an escape — aicr rejects
`--accelerator any` as "no criteria provided", so passing it through would
reproduce the delayed in-pod failure this guard exists to prevent.

The escape clauses are exact, not generous:

- `dataPack` set → the pack owns criteria completeness (its overlays may
  register values the chart cannot know; whether `service: acme` also needs
  an accelerator stated is the pack README's contract, not the chart's).
- `service` + `intent` both set → covers verified accelerator-less embedded
  leaves (`bcm-inference` resolves to 14 components with no accelerator).
  Explicit `accelerator: any` is NOT an escape: aicr rejects it as "no
  criteria provided".

Failure message names all three ways forward. This is the one deliberate
design decision of the release; a zero-config install would otherwise resolve the
thinnest 11-component stack, which is a trap, not a convenience.

### 6.2 Example values

The chart's documented examples always show a full criteria set (the
`eks/gb200/training/ubuntu/kubeflow` 15-component leaf for production; the
catalog keeps its kind CI values). No example demonstrates bare-minimum
criteria.

### 6.3 `environment.*` demotion

`environment.k0sContainerd` and `environment.preinstalledDriver` keep working
unchanged. The README reframes them: these encode environment facts that
belong in an org pack's overlay — the synthetic acme overlay from §1.2 is the
worked example of a bundle needing zero manual flags. New deployments with a
pack should not set them.

### 6.4 README restructure

Order: (1) org-pack path — build a pack (link upstream data-extension docs +
the pack tree from §1.2 as the template), push it as an OCI artifact, deploy
with `dataPack` + private-registry Secret; (2) evidence publishing with the
two modes; (3) "Exploring the upstream matrix" — states plainly: 45 of ~101
entries are leaves, under-specification thins the stack silently,
`aicr recipe list --gpu <x>` is how to check before deploying, and the
`aicr-recipe` ConfigMap is how to check after. Limitations list updated:
remove "public artifacts only"; rewrite the unsigned-evidence bullet to the
two modes; reword the nodewright bullet (operator installed, no `Skyhook`
CRs created, nothing reboots on install alone); air-gap and idempotency
bullets unchanged.

## 7. Guards and testing

### 7.1 Render-time guards (all with actionable messages)

| Condition | Message intent |
|---|---|
| criteria guard from §6.1 trips | the three ways forward: state an accelerator, set a dataPack, or state service+intent |
| `publish.enabled` without `validate.enabled` | publishing needs a validation run |
| `publish.enabled` without `emitEvidence` | nothing to publish |
| `publish.mode` ∉ {signed, unsigned} | list valid values |
| `publish.enabled` with empty `ref` | `--push` is required by aicr |
| `mode=signed`, empty `identityTokenSecret.name` | name the Secret or use unsigned |

### 7.2 Render assertions (`hack/verify-render.sh`, mutation-tested)

- `dataPackSecret` set → volume + `--registry-config` in initContainer; absent by default.
- `mode=signed` → `COSIGN_IDENTITY_TOKEN` via `secretKeyRef`, no `--no-sign`.
- `mode=unsigned` → `--no-sign` present, `COSIGN_IDENTITY_TOKEN` absent.
- `publish.ref` reaches the command line.
- Recipe capture rendered by default; absent when `recipeConfigMap: ""`.
- Criteria guard: rejects empty-everything; accepts each escape clause
  (dataPack set; service+intent set; accelerator set).
- Every §7.1 guard rejects its bad input.

Every assertion is reverted-template tested before it counts — the original
suite had two vacuous assertions and this rule is what caught them.

### 7.3 Cluster tests (kind, offline) — IMPLEMENTED AND RUN

Automated as `hack/e2e/run-kind-e2e.sh` (values: `hack/e2e/values-kind-e2e.yaml`,
pack fixture: `hack/e2e/acme-aicr-pack/`; local-only — see §10).
One authed htpasswd `registry:2` serves both the pack pull and the evidence
push, exercising `dataPackSecret` and `publish.registrySecret` together.

**As-run evidence (2026-08-10, kind v1.34.0, aicr v0.18.0):**

- Pack authored per upstream docs and validated offline first:
  `--debug recipe` resolved, `recipe list --data` showed
  `acme-kind-training … external` as a passing leaf, `--criteria-strict`
  rejected `service: acme` (the CI gate).
- `oras push` → `acme-aicr-pack:1.0.0`, digest `sha256:e780162a…`.
- **Finding (fixed):** the oras initContainer failed with
  `open /tmp/oras_file_…: read-only file system` — oras stages blobs via
  /tmp, which `readOnlyRootFilesystem` denied. The dataPack pull had been
  broken at runtime in every draft; no render assertion could have caught
  it. Fixed with a `pack-tmp` emptyDir mounted at /tmp (asserted).
- Authed, plain-HTTP pull succeeded; pulled digest matched the push exactly.
- Pack-named resolution in-cluster: `service=acme` → 11 components /
  4 overlays, identical to the offline run; recipe slug `h100-acme-training`.
- `aicr-recipe` ConfigMap: criteria + pack ref + resolver summary (421 B)
  + full recipe (68 554 B, under the budget).
- Install: 12 Helm releases, 0 failed, Job Complete exit 0 — without the
  kind overlay's relaxations (the acme chain inherits base+h100).
- Validation: CTRF captured — 4 tests: 2 passed, 1 skipped, 1 inconclusive,
  0 failed.
- **Unsigned publish: exit=0.** Artifact
  `aicr-evidence:h100-acme-training-5a10a4b83ddc` present in the registry
  (authed catalog listing); anonymous access 401s. Pointer captured to the
  evidence ConfigMap (338 B) alongside `evidence.tgz` (16 724 B).
- **Observed:** v0.18.0 `--no-sign` OMITS the `signer` field entirely rather
  than writing an empty block (the help text says "empty signer block").
  The e2e asserts absence; the signed-mode CI assert treats a missing
  signer as failure, which remains correct for signed publishes.
- Negative test: `dataPackSecret=""` → initContainer failed in ~3 s with
  `basic credential not found`. Fail-closed, no anonymous fallback.

`aicr evidence verify` against the pushed bundle was not exercised (needs
registry access from the verifying host plus trust-root setup); tracked as a
possible follow-up assert.

### 7.4 Signed mode

Untestable on kind (public Fulcio will not trust a self-managed issuer's
token). GitHub Actions is the one environment with a free Fulcio-trusted
identity — but a second constraint surfaced during implementation: **GitHub
OIDC tokens live ~5 minutes**, and the chart's publish step runs after
`deploy.sh` plus validation, tens of minutes after any token minted at
install time. A Secret-fed token therefore expires before the in-pod signed
publish would use it — in CI, and in any comparably slow production run.

The signed-path test therefore has to run the signed publish **on the
host**: `aicr validate --emit-attestation` against the cluster, then
`aicr evidence publish` with ambient Actions OIDC — fresh at publish time —
asserting the pointer's signer block is non-empty. Upstream built
`evidence publish` exactly for this split, and the artifact is
content-addressable, so the result is identical to an in-pod signed push.
A release-gated workflow implementing this (`signed-evidence-e2e.yml`) was
built and then removed from CI before the initial release (§10); the
chart's signed-mode *template plumbing* remains covered by the render
assertions, and the in-pod publish *path* by the unsigned kind e2e.

This finding hardens the §9 token-expiry risk from likely to near-certain on
slow installs, and further strengthens the recommendation of `unsigned` mode
for production.

## 8. Versioning and rollout

Version `0.1.0` — the initial published release.

1. Implement; render assertions mutation-tested.
2. kind tests: private pack, unsigned publish, recipe capture.
3. Tag `v0.1.0`; release workflow publishes to `ghcr.io/mirantis/charts`
   (the refuse-to-overwrite guard already covers re-publish accidents).
4. Signed-mode CI test against the tagged artifact. *(Dropped — e2e
   workflows removed from CI before the initial release; §10.)*
5. Follow-up catalog PR: point `apps/aicr` at 0.1.0 (st-charts, charts.yaml,
   example, regenerate wrapper, data.yaml). The catalog's kind e2e keeps
   validation off; its example values already state full criteria, so the
   guard does not affect it.

## 9. Risks

- **Token expiry mid-run** — highest-likelihood operational failure;
  `deploy.sh` can run tens of minutes before validation. Mitigated by docs,
  advisory default (`publish.failOnError: false`), and unsigned mode.
- **Identity token in a cluster-admin pod** — accepted for signed mode by
  explicit decision; unsigned exists for callers who cannot accept it.
- **Criteria guard false positives** — an org pack whose recipes genuinely
  need no accelerator and no intent still trips the guard if the operator
  states only `service`. Escape: any of the three clauses; documented. The
  alternative (no guard) re-opens the thin-default trap for everyone.
- **Recipe/evidence ConfigMap size** — both captures share the existing
  size-guard pattern; the registry copy is authoritative for evidence.
- **aicr CLI drift** — every flag cited here was read from the v0.18.0
  binary, not inferred. `appVersion` bumps must re-run the `--help` checks
  (`recipe`, `evidence publish`, `evidence sign`).

## 10. Decision log

- **Primary user: fleet operator with an org pack.** The pattern is validated
  internally against real hardware; public docs use only the synthetic acme
  example. The chart's story is "install your org's named recipe," not
  "assemble five dimensions."
- **Recipe visibility is report-only.** No preflight step, no expectation
  matching — one Job, resolved recipe captured to a ConfigMap.
- **No default accelerator.** Render guard with three exact escapes; the
  thinnest-stack default was a trap. Deliberate initial-release decision.
- **Signing identity is BYO via Secret** — public Fulcio does not trust
  self-managed k0s issuers, so projected SA tokens fail exactly where k0rdent
  lives.
- **Both publish modes ship** (`publish.mode`), one flag apart; materially
  different security postures, both legitimate.
- **`pointer.yaml` rides the existing evidence ConfigMap** as a second key.
- **Signed path tested in GitHub Actions** — the one free Fulcio-trusted
  environment.
- **e2e workflows removed from CI before the initial release** (2026-08-11).
  `kind-e2e.yml` (PR-gated) and `signed-evidence-e2e.yml` (release-gated)
  were unreliable on hosted runners for infrastructure reasons: a 4-vCPU
  node sits at ~99% CPU-requested after the `--no-wait` full-stack install,
  leaving aicr's snapshot-agent pod unschedulable, and in-cluster pulls of
  the agent image can stall inside `aicr validate`'s timeout window.
  Removed rather than demoted to manual; `hack/e2e/run-kind-e2e.sh` — which
  side-loads the agent image into the kind node to avoid the pull stall —
  is the pre-release entry point until a CI replacement exists. Release
  gating (lint, render assertions, tag/version guard, refuse-to-overwrite)
  is unchanged; neither e2e workflow ever gated the release.
- **`environment.*` demoted, not removed** — compatibility kept; packs are the
  right home for environment facts.
- **One merged spec** — this document supersedes the standalone
  datapack/evidence draft of the same date; the vision is the justification
  for the features, so they live together.
- **`imagePullSecrets` excluded** as unrelated scope.
